## 背景："为什么我被封了？"

做过风控对抗的一定经历过这种时刻：

> 所有设备参数都改好了，账号也养了一段时间，一切看起来正常……突然就被封了。翻来覆去排查，找不到原因，最后只能归咎于"风控太强"或"运气不好"。

风控对抗不应该是一门"玄学"。每一个检测点都可以被定位、被理解、被绕过。关键在于建立**系统化的分析框架**。

## 1. 风控体系全景

### 1.1 现代风控的多层架构

```
Layer 6: 业务规则引擎 —— 特定业务逻辑检测
Layer 5: 行为模型 —— 用户操作模式分析
Layer 4: 环境检测 —— 设备指纹 + 运行环境
Layer 3: 网络分析 —— IP + DNS + TLS
Layer 2: 账号关联 —— 同设备/同网络/同行为
Layer 1: 基础校验 —— 参数合法性
```

### 1.2 云手机/虚拟设备的风控痛点

对于 CVD 云手机方案，风控最关注的是：

| 检测层 | 核心问题 | 难度 |
|--------|----------|------|
| 环境检测 | 你是否在虚拟设备上运行？ | ★★★ |
| 设备指纹 | 你的设备信息是否"合理"？ | ★★★★ |
| 行为模型 | 你的操作是否像正常人？ | ★★★★★ |
| 账号关联 | 你是否在批量操作？ | ★★★★ |

## 2. 设备指纹对抗：最核心的战场

### 2.1 设备指纹的构成

设备指纹 = 主动采集的设备属性 + 被动暴露的系统特征。

**主动采集**（风控 SDK 主动查询）：

```
系统属性    → Build.getSerial(), Build.getFingerprint(), Build.MODEL
硬件标识    → Settings.Secure.ANDROID_ID, MAC 地址, IMEI/MEID
传感器      → SensorManager.getSensorList() 返回的传感器类型和参数
文件系统    → /system/build.prop, /vendor/build.prop 的存在和内容
应用列表    → PackageManager.getInstalledPackages() 检查特定应用
```

**被动暴露**（风控通过侧信道推断）：

```
/proc/cpuinfo      → CPU 型号（如果显示 QEMU/KVM 则暴露）
/proc/meminfo      → 内存大小是否合理
/sys/class/net/    → 网络接口（eth0 vs wlan0）
/sys/devices/      → 设备树信息
mmap / syscall     → 系统调用特征（虚拟化有特殊行为）
```

### 2.2 常见风控检测手法解析

#### 检测点 1：`ro.build.fingerprint` 校验

```java
// 风控 SDK 常见逻辑
String fingerprint = Build.FINGERPRINT;
// 期望格式: "brand/product/device:version/id/build_number:type/tags"
// 如: "google/oriole/oriole:14/UP1A.231005.007/10865277:user/release-keys"

// 检测逻辑：
// 1. 格式是否合法（至少有 4 个 / 分隔符）
// 2. brand/product/device 是否互相对应
// 3. tags 是否为 "release-keys"（非 test-keys 或 dev-keys）
// 4. type 是否为 "user"（非 userdebug 或 eng）
```

**对抗方案**：使用真实机型的完整 fingerprint，而非自定义拼接。

#### 检测点 2：ADB/USB 调试状态

```java
// 多个检测点并联
int adbEnabled = Settings.Global.getInt(cr, Settings.Global.ADB_ENABLED, 0);
boolean usbConnected = getUsbConnectedStatus();
String bootloaderStatus = SystemProperties.get("ro.boot.verifiedbootstate");

// 三者交叉验证：
// ADB_ENABLED=1 + USB_CONNECTED=true → 高度可疑
// verifiedbootstate=orange → Bootloader 已解锁 → 高风险
```

**对抗方案**：
- ADB：在系统服务层返回值恒为 0（但保持 adbd 运行）
- USB：Hook UsbManager 返回空设备列表
- Bootloader：如果不是物理设备，修改内核启动参数

#### 检测点 3：传感器列表分析

```java
SensorManager sm = (SensorManager) getSystemService(SENSOR_SERVICE);
List<Sensor> sensors = sm.getSensorList(Sensor.TYPE_ALL);

// 检测逻辑：
// 1. 传感器数量是否异常（虚拟设备通常传感器很少）
// 2. 传感器供应商名称是否为 "Google" 或 "Goldfish"
// 3. 是否缺少关键传感器（加速度计、陀螺仪、磁力计）
// 4. 传感器参数（分辨率、范围、功耗）是否合理
```

**对抗方案**：在 CVD 的传感器 HAL 中注册更多传感器，并设置合理的供应商名和参数。

#### 检测点 4：GPU/显示子系统

```java
// EGL 查询
String renderer = GLES20.glGetString(GLES20.GL_RENDERER);
String vendor = GLES20.glGetString(GLES20.GL_VENDOR);

// 检测逻辑：
// 如果 renderer 包含 "virgl", "swiftshader", "llvmpipe" → 确定是虚拟设备
// 如果 vendor 为 "Google" 或 "Mesa" → 高度可疑
// 如果缺少 Vulkan 支持 → 可能是旧版虚拟化
```

**对抗方案**：替换 EGL/GLES 库中的字符串，编译时修改 GPU HAL。

### 2.3 看雪社区中的经典分析

根据看雪安全社区的公开分析文章，大厂风控引擎通常在以下层面部署检测点：

| 检测层 | 检测内容 | 实现方式 |
|--------|----------|----------|
| Java 层 | 系统属性、Build 信息 | 标准 Android API |
| Native 层 | `/proc` 文件读取、syscall 特征 | JNI + 直接 syscall |
| 内核层 | readlinkat, stat, openat 特征 | 直接 syscall 绕过 libc |
| seccomp | 限制进程可用的系统调用 | BPF 过滤器 |

核心思路：**从低到高逐层检测，一旦任何一层发现异常，立即标记**。

## 3. 网络维度对抗

### 3.1 IP 风险评分

风控系统会给每个 IP 地址打分：

```
IP 类型:
  - 数据中心 IP    → 高风险 (托管服务器)
  - 住宅代理 IP    → 中风险
  - 家庭宽带 IP    → 低风险
  - 移动网络 IP    → 低风险

IP 行为历史:
  - 短时间内关联多个账号  → 高风险
  - 长期只有一个账号      → 低风险
```

### 3.2 DNS 泄露检测

即使配置了代理，DNS 查询也可能泄露设备信息：

```bash
# 在 CVD 中检查 DNS 配置
adb shell getprop | grep dns
# net.dns1
# net.dns2
# dhcp.wlan0.dns1

# DNS 泄露示例：
# 代理 IP 在美国，但 DNS 查询走的是中国运营商 DNS
# → 风控判定：代理行为
```

**对抗方案**：确保 DNS 也通过代理或使用与出口 IP 一致的 DNS 服务器。

### 3.3 TCP/IP 栈指纹

不同操作系统的 TCP/IP 栈有不同的行为特征：

```
Windows TCP/IP 栈:
  - TTL 默认值: 128
  - TCP Window Size: 65535
  - 拥塞控制算法: NewReno

Linux TCP/IP 栈 (Android 基于此):
  - TTL 默认值: 64
  - TCP Window Size: 取决于配置
  - 拥塞控制算法: BBR 或 Cubic

检测方法:
  - p0f, JA3, JA4+ 等被动指纹识别工具
  - 检测 TLS ClientHello 中的密码套件顺序
```

CVD 基于 Linux，TCP/IP 栈天然与 Android 真机一致，这是它的优势。

## 4. 单账号行为模型

### 4.1 行为建模的核心指标

风控不只是检查"你是谁"，更重要的是"你做了什么"：

```
注册行为:
  - 注册到首次操作的间隔（机器人通常极短）
  - 注册设备是否是"新设备"（无历史数据）
  - 注册 IP 的归属地与手机号归属地是否匹配

操作行为:
  - 点击坐标分布（人类点击有自然偏移，脚本点击精确）
  - 操作时间间隔（人类有变化，脚本恒定）
  - 页面停留时间（正常浏览 vs 快速跳转）
  - 滑动轨迹（人类有加速度变化，脚本匀速）

内容行为:
  - 发布内容的语义一致性
  - 关注/加好友的模式
  - 消息发送频率和内容多样性
```

### 4.2 对抗思路

| 行为特征 | 脚本特征 | 人类特征增强方案 |
|----------|----------|-----------------|
| 点击坐标 | 精确到 (540, 960) | 高斯分布随机偏移 ±10px |
| 操作间隔 | 固定 500ms | 指数分布随机延迟 200-3000ms |
| 滑动轨迹 | 匀速直线 | 贝塞尔曲线 + 加减速 |
| 页面停留 | < 100ms | 根据页面内容动态计算停留时间 |

## 5. 多账号行为模型 —— 矩阵分析

### 5.1 账号关联图谱

风控会构建账号之间的关联图：

```
账号 A ←──同设备──→ 账号 B
  │                   │
同IP                同WiFi
  │                   │
  v                   v
账号 C ←──同操作──→ 账号 D
```

一旦某个账号被标记违规，同图中的其他账号也会被关联审查。

### 5.2 矩阵风控的核心逻辑

```
阈值模型:
  单设备/单IP → N 个账号/天 → 超过阈值 → 所有账号封禁

  示例:
  - 阈值: 5 个账号/设备/天
  - 实际: 第 6 个账号注册时
  - 结果: 该设备上的前 5 个账号也全部进入风控审查
```

**对抗方案**：
- 每个 CVD 实例 = 一个独立设备（不同指纹）
- 每个实例对应独立 IP
- 账号操作模式（注册/活跃时间/操作频率）各实例间差异化

## 6. 构建系统化的风控对抗框架

### 6.1 从"盲改"到"工程化"

很多人的做法是"猜——改——试——被封——再猜"，缺乏系统化方法。更好的步骤是：

```
1. [定位] 确定风控 SDK 的检测维度
   ↓
2. [验证] 逐维度测试，确认哪些参数被检测
   ↓
3. [量化] 找出每个维度的阈值和判定逻辑
   ↓
4. [对抗] 精确修改被检测的参数
   ↓
5. [测试] 小规模验证通过后，再扩大规模
```

### 6.2 检测维度定位的方法

#### 方法一：Hook + 日志

```javascript
// Frida 脚本：监控所有属性读取
Java.perform(function() {
    var SystemProperties = Java.use("android.os.SystemProperties");
    SystemProperties.get.overload('java.lang.String').implementation = function(key) {
        var result = this.get(key);
        console.log("[PROP] get(" + key + ") = " + result);
        return result;
    };
    
    // 监控 Build 类字段访问
    var Build = Java.use("android.os.Build");
    // ... hook 关键字段
});
```

#### 方法二：代码反编译 + 静态分析

```bash
# 反编译目标 App 的风控 SDK
jadx target.apk -d output/

# 搜索关键 pattern
grep -r "Build\." output/
grep -r "SystemProperties" output/
grep -r "/proc/" output/
grep -r "getSensorList" output/
grep -r "ADB_ENABLED" output/
```

#### 方法三：差分测试

```
步骤:
1. 在真机上运行 App，记录所有检测项的返回值
2. 在 CVD 上运行 App，记录相同检测项的返回值
3. 逐项比对差异 → 找出被检测的维度
4. 逐个修改差异项 → 观察哪些修改触发了风控反应
```

### 6.3 对抗层级总结

```
优先级 (从容易到困难):

Level 1: 系统属性伪造
  - build.prop / default.prop
  - 难度: ★★☆☆☆ · 效果: ★★☆☆☆

Level 2: Java/Native API Hook
  - Frida / LSPosed / Xposed
  - 难度: ★★★☆☆ · 效果: ★★★☆☆

Level 3: 文件系统伪装
  - /proc /sys 下的文件内容
  - 难度: ★★★★☆ · 效果: ★★★★☆

Level 4: 内核级对抗
  - KernelSU / APatch / 自编译内核
  - 难度: ★★★★★ · 效果: ★★★★★

Level 5: 硬件抽象层 (HAL) 定制
  - GPU HAL / Sensor HAL / RIL HAL
  - 难度: ★★★★★ · 效果: ★★★★★
```

## 7. 完整链路回顾

把五篇内容串联起来，完整的 CVD 云手机定制与风控对抗链路是：

```
[硬件层] CVD + KVM
    ↓
[系统层] AOSP 源码编译 + 系统属性定制
    ↓
[应用层] GMS 集成 + WebView 替换
    ↓
[内核层] KernelSU/APatch + SuSFS + cpuinfo 定制
    ↓
[网络层] 透明代理 + SSL Pinning 绕过 + 网络一致性
    ↓
[风控层] 设备指纹 → 网络维度 → 行为模型 → 账号矩阵
```

每一层的修改都要保证**逻辑一致性**——这是风控对抗最关键的原则。

---

## 结语

这一系列博客覆盖了从 CVD 环境搭建到风控对抗分析的完整技术链路。核心要点：

1. **CVD 是真正的"可控环境"**——可以改到内核层，不是模拟而是真实 Android 系统
2. **系统级定制是基础**——build.prop、ADB 隐藏、设备指纹这些是入门关
3. **内核级定制拉开差距**——GKI/KMI 是门槛，SuSFS 和 APatch KPM 是进阶
4. **网络一致性是容易被忽略的关键**——设备参数、定位、时区、IP 必须匹配
5. **风控对抗需要系统化思维**——定位→验证→量化→对抗→测试，而不是盲猜
