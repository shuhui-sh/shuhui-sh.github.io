> 这一篇覆盖 GKI/KMI 概念、KernelSU、SuSFS、APatch、cpuinfo 定制等核心主题。

## 背景：为什么系统层不够，必须动内核？

在系统层改了 build.prop、隐藏 ADB、替换了 WebView……但风控仍然能检测到你。

原因是风控 SDK 不会只查 Java 层 API。现代风控方案会直接读取：

```
/proc/cpuinfo          # CPU 型号/核心数/架构
/proc/meminfo          # 内存信息
/proc/version          # 内核版本
/sys/class/net/        # 网络接口
/sys/devices/          # 设备树信息
```

这些 `/proc` 和 `/sys` 下的信息**不是由 Java 框架提供的，而是由 Linux 内核直接暴露的**。不修改内核，系统层的修改就是"掩耳盗铃"。

---

## 1. 基础概念：GKI、KMI、LKM、ACK

这是理解内核级定制的四个基石概念。

### 1.1 GKI (Generic Kernel Image)

Google 在 Android 12 引入的核心架构变革。

**问题背景**：在 GKI 之前，每款手机的 Linux 内核都是高度定制化的，SoC 厂商和 OEM 在 ACK (Android Common Kernel) 上添加了大量自己的代码。这导致：

- 安全补丁无法统一部署
- 内核碎片化严重（高达 50% 的代码是 out-of-tree 的）
- 大版本升级困难

**GKI 的解决方案**：将内核分为两部分——

```
┌──────────────────────────────────────┐
│       GKI 内核 (Google 统一维护)      │
│  - 不包含 SoC/主板相关代码            │
│  - 单一内核二进制文件                 │
│  - 与 Android 平台版本解耦            │
├──────────────────────────────────────┤
│         Vendor Module (厂商维护)      │
│  - SoC 驱动                          │
│  - 主板驱动                          │
│  - 通过稳定的 KMI 接口与 GKI 通信     │
└──────────────────────────────────────┘
```

### 1.2 KMI (Kernel Module Interface)

KMI 是 GKI 内核暴露给 Vendor Module 的**稳定接口**。

关键特性：
- 相同 KMI 版本的内核**二进制兼容**
- Vendor Module 可以在不重新编译的情况下工作
- GKI 内核可以独立更新而不影响 Vendor Module

**查看 KMI 版本**：

```bash
adb shell uname -r
# 示例输出: 5.10.101-android12-9-g30979850fc20
# KMI 版本: 5.10-android12-9
# 格式: Version.PatchLevel-AndroidRelease-KmiGeneration
```

**关键理解**：`SubLevel`（如上例中的 `101`）**不是 KMI 的一部分**。这意味着 `5.10.101-android12-9` 和 `5.10.137-android12-9` 的 KMI 是相同的，可以互换内核。

### 1.3 LKM (Loadable Kernel Module)

LKM 是可以**动态加载**到内核中的代码模块。在 GKI 架构下，SoC 驱动以 LKM 形式存在于 `/lib/modules/` 目录。

对定制而言，LKM 的优势是不需要替换启动镜像（boot.img），风险更低。KernelSU 在 v0.9.0 之后同时支持 GKI 模式（替换内核）和 LKM 模式（加载模块）。

### 1.4 ACK (Android Common Kernel)

ACK 是 Google 维护的 Android 内核分支，是所有 GKI 内核的上游来源。

```bash
# 查看当前 ACK 分支
git clone https://android.googlesource.com/kernel/common
cd common
git branch -a | grep android
```

## 2. KernelSU：内核级 Root 方案

### 2.1 KernelSU vs Magisk

| 特性 | Magisk | KernelSU |
|------|--------|----------|
| 运行层级 | 用户空间 (userspace) | 内核空间 (kernel space) |
| Root 实现 | 修改 boot.img + su 守护进程 | 内核级权限控制 |
| 隐蔽性 | 中等（需搭配 Shamiko 等） | **高**（内核级，更难被检测） |
| 权限管理 | Superuser 列表管理 | UID-based 细粒度控制 |
| GKI 兼容 | 需要适配 | **原生支持 GKI** |
| 卸载 | 刷回原 boot.img | LKM 模式可直接卸载不重启 |

### 2.2 KernelSU 的两种工作模式

#### GKI 模式

直接用 KernelSU 提供的 GKI 内核替换设备的原始内核：

```bash
# 1. 下载 KernelSU Manager 查看支持状态
# 2. 从 GitHub Release 下载对应 KMI 的 boot.img
# 3. 刷入
fastboot flash boot boot-ksu.img
fastboot reboot
```

**优点**：通用性强，不依赖官方固件
**缺点**：需要替换内核，有变砖风险

#### LKM 模式

不替换内核，只加载内核模块：

```bash
# 1. 获取官方 boot.img
# 2. 用 KernelSU Manager 的 LKM 功能打补丁
# 3. 刷入修补后的 boot.img 并加载模块
```

**优点**：不需要替换内核，支持 OTA，可随时卸载
**缺点**：部分设备（如三星 KNOX）不兼容

### 2.3 安装 KernelSU LKM 模式

```bash
# 1. 从官方固件提取 boot.img
# 2. 使用 KernelSU Manager App 修补
#    选择 "LKM Mode" → 选择 boot.img → 等待修补完成
# 3. 刷入
fastboot flash boot patched_boot.img
fastboot reboot
# 4. 安装 KernelSU Manager APK
# 5. 打开 Manager → 安装 LKM 模块
```

更详细的官方指南：<https://kernelsu.org/guide/installation.html>

## 3. SuSFS：内核级文件隐藏

### 3.1 SuSFS 是什么

SuSFS (SUper Secure FileSystem) 是一个内核补丁，提供**内核级别的文件和目录隐藏能力**。

**为什么需要它？**

普通的文件隐藏（如 Magisk 的 mount namespace 隔离）只在用户空间生效。风控 SDK 如果通过以下方式检测，Magisk 无法防御：

```c
// 直接 syscall 读取文件（绕过 libc）
int fd = syscall(__NR_openat, AT_FDCWD, "/system/xbin/su", O_RDONLY);
// SuSFS 在内核层拦截 openat 系统调用，返回 ENOENT
```

### 3.2 SuSFS 核心功能

| 功能 | 说明 |
|------|------|
| 文件隐藏 | 对指定路径返回"文件不存在" |
| 目录隐藏 | 对指定目录内容进行过滤 |
| 进程隐藏 | 隐藏特定进程的 /proc 条目 |
| Mount 隐藏 | 隐藏异常挂载点 |
| UID/GID 劫持 | 修改进程的 UID 返回 |

### 3.3 编译集成 SuSFS 到 GKI 内核

以 Pixel 7a + android14-6.1 为例：

```bash
# 1. 创建工作目录
mkdir workarea && cd workarea

# 2. 克隆 susfs4ksu
git clone --depth 3 --no-tags \
  https://gitlab.com/pershoot/susfs4ksu.git \
  -b gki-android14-6.1-dev

# 3. 创建并初始化内核源码目录
mkdir gki-kernel && mkdir android-kernel
cd gki-kernel

# 4. 拉取 Android GKI 源码
repo init -u https://android.googlesource.com/kernel/manifest --depth=3
# 从 ci.android.com 获取对应 manifest_xxxxx.xml
cp -p ../manifest_xxxxx.xml .repo/manifests
repo init -m manifest_xxxxx.xml --depth=3
repo sync -c --no-tags
cd ..

# 5. 创建镜像并复制 SuSFS 补丁
rsync -a --del gki-kernel/ gki-14
cd gki-14
cp -p ../susfs4ksu/kernel_patches/fs/* common/fs
cp -p ../susfs4ksu/kernel_patches/include/linux/* common/include/linux
cp -p ../susfs4ksu/kernel_patches/50_add_susfs_in_gki-android14-6.1.patch common
cp -p ../susfs4ksu/kernel_patches/60_scope-minimized_manual_hooks.patch common

# 6. 打补丁
cd common
patch -p1 -ui 50_add_susfs_in_gki-android14-6.1.patch
patch -p1 -ui 60_scope-minimized_manual_hooks.patch
cd ..

# 7. 集成 KernelSU-Next
curl -LSs "https://raw.githubusercontent.com/pershoot/KernelSU-Next/refs/heads/next-susfs/kernel/setup.sh" \
  | bash -s next-susfs

# 8. 提交修改并编译
cd common
git add -A && git commit -a -m "Add KernelSU-Next-susfs"
cd ..

tools/bazel run --config=fast --config=stamp --lto=thin \
  //common:kernel_aarch64_dist -- --dist_dir=../android-kernel

# 9. 刷入编译产物
fastboot flash boot android-kernel/Image.lz4
```

详细教程参考：[Droid Basement - KSU-Next + SuSFS 集成教程](https://droidbasement.com/db-blog/tutorial-kernelsu-next-with-susfs-integrated-in-to-a-gki-generic-kernel-image/)

## 4. APatch：新一代内核级 Root

### 4.1 APatch vs KernelSU vs Magisk

| 特性 | Magisk | KernelSU | APatch |
|------|--------|----------|--------|
| 运行层级 | Userspace | Kernel space | Kernel + Userspace |
| 内核支持 | 3.18+ | GKI only | 3.18 - 6.12 |
| SELinux | 依赖策略修改 | 可选不修改 | 可选不修改 |
| GKI 依赖 | 不依赖 | 强依赖 | 可选 |
| KPM 支持 | 无 | 有限 | **完整 KPM 框架** |

### 4.2 APatch 独特优势

1. **KPModule (KPM)**：APatch 的核心竞争力，允许开发者编写内核模块，在内核空间执行任意代码
2. **不修改 SELinux**：可选不触碰 SELinux 策略，更高的隐蔽性
3. **广泛兼容**：支持内核版本 3.18 ~ 6.12，不限于 GKI 设备

### 4.3 APatch 安装

```bash
# 1. 检查内核支持 (需要 root)
adb shell
su -c "zcat /proc/config.gz | grep -w CONFIG_KALLSYMS"
# 输出 CONFIG_KALLSYMS=y 则支持

# 2. 从 GitHub Release 下载 APatch Manager
# https://github.com/bmax121/APatch/releases

# 3. 使用 APatch Manager 修补 boot.img
# 选择 "Patch" → 选择 boot.img → 等待完成

# 4. 刷入
fastboot flash boot patched_boot.img
fastboot reboot
```

官方文档：<https://apatch.dev/>

## 5. cpuinfo 定制

`/proc/cpuinfo` 是风控最常检测的文件之一。它暴露了 CPU 的完整信息：

```bash
adb shell cat /proc/cpuinfo
```

CVD 默认的 cpuinfo 会显示虚拟化特征（如 QEMU Virtual CPU、KVM 标识等），这是明显的虚拟设备标记。

### 5.1 内核源码层面修改

修改 `arch/arm64/kernel/cpuinfo.c`（ARM64）：

```c
// 替换 cpuinfo 显示的字符串
static int c_show(struct seq_file *m, void *v)
{
    // 原: seq_printf(m, "processor\t: %d\n", i);
    // 原: seq_printf(m, "CPU architecture: 8\n");
    
    // 改为伪造特定 SoC 的信息
    seq_printf(m, "Hardware\t: Qualcomm SM8550\n");
    seq_printf(m, "CPU implementer\t: 0x51\n");    // Qualcomm
    seq_printf(m, "CPU architecture: 8\n");
    seq_printf(m, "CPU variant\t: 0x3\n");
    seq_printf(m, "CPU part\t: 0x001\n");
    seq_printf(m, "CPU revision\t: 4\n");
}
```

### 5.2 通过 APatch KPM / KernelSU 模块修改

APatch 的 KPM 框架可以直接 hook 内核函数：

```c
// KPM 示例：修改 cpuinfo 输出
static int hooked_c_show(struct seq_file *m, void *v)
{
    // 过滤掉虚拟化特征字符串
    // 替换为伪造的 SoC 信息
    return 0;
}

// 使用 kprobe hook seq_file_operations
```

## 6. SoC 簇调度策略伪装

现代 Android SoC 使用 big.LITTLE 或 DynamIQ 架构，有不同的 CPU 簇（clusters）。风控可能通过分析 `/sys/devices/system/cpu/` 下的拓扑信息来识别虚拟设备。

```bash
# 查看 CPU 拓扑
adb shell cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_available_frequencies
adb shell cat /sys/devices/system/cpu/possible

# 真机典型输出 (Snapdragon 8 Gen 2):
# possible: 0-7
# cpu0-3: Cortex-A510 (效率核)
# cpu4-6: Cortex-A715 (性能核)  
# cpu7: Cortex-X3 (超大核)
```

CVD 默认的 CPU 拓扑是平坦的（没有簇区分），需要在内核配置中定制：

```bash
# 编辑内核 defconfig
# arch/arm64/configs/gki_defconfig
CONFIG_SCHED_MC=y
CONFIG_ARM64_CPUIDLE=y
CONFIG_CPU_FREQ=y
```

## 7. 在 CVD 上运行自定义内核

CVD 支持直接替换内核镜像，这是它的核心优势之一：

```bash
# 编译自定义内核
cd kernel/common-android14-6.1
tools/bazel run //common-modules/virtual-device:virtual_device_x86_64_dist

# 使用自定义内核启动 CVD
launch_cvd \
  --kernel_path=./out/virtual_device_x86_64/dist/bzImage \
  --initramfs_path=./out/virtual_device_x86_64/dist/initramfs.img

# ARM64 版本
launch_cvd \
  --kernel_path=./out/virtual_device_aarch64/dist/Image \
  --initramfs_path=./out/virtual_device_aarch64/dist/initramfs.img

# 开发迭代流程
# 修改内核 → make → launch_cvd --kernel_path=... → 验证 → 重复
```

## 总结：内核定制能力矩阵

| 层级 | 技术 | 风控对抗能力 |
|------|------|-------------|
| L1 | Magisk + Shamiko | 拦截应用层检测（银行App、SafetyNet） |
| L2 | KernelSU LKM | 内核空间 Root，更高隐蔽性 |
| L3 | KernelSU GKI + SuSFS | 内核级文件/进程/挂载隐藏 |
| L4 | APatch + KPM | 任意内核函数 Hook，完全自由定制 |
| L5 | 自编译内核 + 源码修改 | 从源头消除虚拟化特征，终极方案 |
