> 前三篇解决了系统和内核层的问题。现在到了风控绕不开的另一半——网络层。
> 核心目标不是"挂代理"，而是让网络行为与设备环境保持一致性。

---

## 背景：为什么网络层会被单独检测？

风控系统在分析一个请求时，会做**多维度交叉验证**：

```
请求来源 IP 归属地: 北京
  ×
设备 GPS/基站定位: 深圳
  ×
SIM 卡运营商: 中国移动 (MCC=460, MNC=01)
  ×
时区设置: America/New_York
  →
风控结论: 异常
```

即使设备和系统信息伪造得很好，一旦网络特征与环境不匹配，整个会话就会被标记为异常。

## 1. 风控系统的网络维度检测面

```
┌──────────────────────────────────────────────────────┐
│              网络维度检测点                             │
├──────────────┬───────────────┬───────────────────────┤
│   IP 层      │   传输层       │   应用层               │
├──────────────┼───────────────┼───────────────────────┤
│ IP 归属地    │ TCP 指纹       │ TLS 握手特征           │
│ IP 类型      │ TTL/Hop Limit  │ 证书链                  │
│ 代理检测      │ 窗口大小       │ HTTP Header 顺序       │
│ DNS 泄露      │ 时间戳        │ SNI 与 Host 一致性      │
│ MTU 特征      │ 拥塞算法       │ User-Agent 指纹         │
└──────────────┴───────────────┴───────────────────────┘
```

## 2. CVD 的网络架构

### 2.1 CVD 默认网络拓扑

```
┌──────────┐      ┌─────────────────┐      ┌──────────┐
│   CVD    │──────│  虚拟网桥 (cvd)  │──────│  宿主机  │
│ (guest)  │      │  192.168.0.0/24  │      │   NAT    │
└──────────┘      └─────────────────┘      └──────────┘
                                             │
                                         因特网
```

CVD 默认使用 NAT 模式，所有实例共享宿主机的网络出口。

### 2.2 每个 CVD 实例的网络配置

```bash
# 查看 CVD 实例的网络
adb shell ifconfig
# wlan0: 192.168.0.x/24 (虚拟 WiFi)
# lo: 127.0.0.1

adb shell ip route
# default via 192.168.0.1  # 网关为虚拟网桥

# 查看 DNS
adb shell getprop net.dns1
```

## 3. 代理方案设计

### 3.1 CVD 内代理 vs CVD 外代理

```
方案 A: CVD 内代理
┌─────────────────────────────────────┐
│  CVD                                │
│  App → [代理客户端(如 Clash)] → 出口  │
└─────────────────────────────────────┘
  ├── 优点：代理在设备内部，网络栈一致
  └── 缺点：代理 App 本身可能被风控检测


方案 B: CVD 外代理
┌──────────┐      ┌──────────────┐
│   CVD    │──────│  宿主机代理    │
│  (NAT)   │      │  (mitmproxy)  │
└──────────┘      └──────────────┘
  ├── 优点：代理完全对 CVD 透明
  └── 缺点：需要处理 SSL Pinning 等问题
```

### 3.2 方案 A 实现：CVD 内透明代理

在 CVD 内部运行代理客户端，通过 iptables 实现透明代理：

```bash
# 在 CVD 内安装代理客户端
adb install clash-meta.apk

# 或通过命令行配置 iptables 透明代理
adb shell su -c "
  iptables -t nat -A OUTPUT -p tcp --dport 80 -j REDIRECT --to-port 7890
  iptables -t nat -A OUTPUT -p tcp --dport 443 -j REDIRECT --to-port 7890
"
```

### 3.3 方案 B 实现：CVD 外代理（宿主机侧）

CVD 的网络流量经过虚拟网桥，可以在宿主机侧进行拦截：

```bash
# 1. 查看 CVD 网桥接口
ip addr show cvd-wbr-0
# 获取网桥 IP 段

# 2. 在宿主机启动 mitmproxy 透明代理模式
mitmproxy --mode transparent --listen-port 8080

# 3. 将 CVD 流量重定向到 mitmproxy
iptables -t nat -A PREROUTING \
  -i cvd-wbr-0 -p tcp --dport 80 -j REDIRECT --to-port 8080
iptables -t nat -A PREROUTING \
  -i cvd-wbr-0 -p tcp --dport 443 -j REDIRECT --to-port 8080
```

## 4. mitmproxy 流量劫持实战

mitmproxy 是最常用的开源 HTTPS 代理工具，支持 Python 脚本扩展。

### 4.1 安装 mitmproxy

```bash
# Linux
sudo apt install mitmproxy
# 或
pip install mitmproxy

# macOS
brew install mitmproxy

# Windows
pip install mitmproxy
```

### 4.2 基本抓包配置

```bash
# 启动 mitmweb (Web 界面)
mitmweb --listen-port 8080

# 在 CVD 中配置代理
adb shell settings put global http_proxy 192.168.0.1:8080
# 192.168.0.1 是网关，即宿主机的网桥地址

# 安装 mitmproxy CA 证书到 CVD
# 1. 浏览器访问 mitm.it 下载证书
# 2. 或将证书推送到设备
adb push ~/.mitmproxy/mitmproxy-ca-cert.cer /sdcard/
adb shell am start -a android.intent.action.VIEW \
  -d "content://com.android.externalstorage.documents/document/primary:mitmproxy-ca-cert.cer"
```

### 4.3 使用 mitmproxy 脚本进行高级分析

```python
# interceptor.py
import mitmproxy.http
from mitmproxy import ctx

class RequestInterceptor:
    def request(self, flow: mitmproxy.http.HTTPFlow):
        # 修改 User-Agent 使之一致
        flow.request.headers["User-Agent"] = (
            "Mozilla/5.0 (Linux; Android 14; SM-S9180) "
            "AppleWebKit/537.36 (KHTML, like Gecko) "
            "Chrome/120.0.6099.144 Mobile Safari/537.36"
        )

    def response(self, flow: mitmproxy.http.HTTPFlow):
        # 记录风控相关请求头
        ctx.log.info(f"URL: {flow.request.url}")
        ctx.log.info(f"Response Headers: {flow.response.headers}")

addons = [RequestInterceptor()]
```

```bash
# 使用脚本启动
mitmproxy -s interceptor.py --mode transparent
```

## 5. 证书绑定 (SSL Pinning) 绕过

绝大多数 App（尤其是金融/社交类）都实现了 SSL Pinning，mitmproxy 等中间人代理会被直接拒绝。

### 5.1 SSL Pinning 原理

```
正常连接:
  App ────TLS─────── 服务器
  (App 验证服务器证书是否匹配内置指纹)

中间人代理:
  App ──TLS── mitmproxy ──TLS── 服务器
  (App 收到 mitmproxy 的伪造证书，校验失败 → 拒绝连接)
```

### 5.2 绕过方案一：Frida 动态 Hook

```javascript
// ssl_pinning_bypass.js
Java.perform(function() {
    // 通用 SSL Pinning 绕过
    var TrustManagerImpl = Java.use('com.android.org.conscrypt.TrustManagerImpl');
    TrustManagerImpl.verifyChain.implementation = function(
        untrustedChain, trustAnchorChain, host, clientAuth, endpoint, callback
    ) {
        console.log('[+] SSL Pinning Bypassed for: ' + host);
        // 不做任何验证，直接返回成功
        return;
    };

    // 更通用的方法：Hook 所有 checkServerTrusted
    var X509TrustManager = Java.use('javax.net.ssl.X509TrustManager');
    // ...
});
```

```bash
# 使用
frida -U -f com.target.app -l ssl_pinning_bypass.js --no-pause
```

### 5.3 绕过方案二：APK 反编译 + 修改

```bash
# 使用 apktool 反编译
apktool d target.apk -o target_src

# 修改 AndroidManifest.xml，添加 networkSecurityConfig
# 或在 smali 代码中删除证书验证逻辑

# 重新打包签名
apktool b target_src -o target_patched.apk
jarsigner -verbose -keystore debug.keystore target_patched.apk androiddebugkey
```

### 5.4 绕过方案三：Objection（推荐入门）

Objection 是基于 Frida 的自动化工具，内置了大量绕过脚本：

```bash
# 安装
pip install objection

# 自动绕过 SSL Pinning
objection -g com.target.app explore -s "android sslpinning disable"

# 更详细的分析
objection -g com.target.app explore
# 进入交互模式后:
# android hooking list classes
# android hooking watch class com.target.app.network.ApiClient
```

## 6. 代理检测与对抗

### 6.1 风控如何检测代理

```java
// 方法1：检查系统代理设置
String proxyHost = System.getProperty("http.proxyHost");
int proxyPort = Integer.parseInt(System.getProperty("http.proxyPort", "-1"));
if (proxyPort != -1) {
    // 检测到代理
}

// 方法2：通过 ConnectivityManager 检测
ConnectivityManager cm = getSystemService(ConnectivityManager.class);
NetworkCapabilities nc = cm.getNetworkCapabilities(cm.getActiveNetwork());
// 检测网络是否为 VPN 或代理

// 方法3：发送探测请求
// 请求一个已知 IP，检查 TLS 证书是否匹配预期
```

### 6.2 对抗策略

| 检测方式 | 对抗方案 |
|----------|----------|
| 系统代理属性 | 使用透明代理（不设置系统代理） |
| ConnectivityManager | Hook ConnectivityManager API |
| TLS 证书检查 | SSL Pinning 绕过 |
| 代理端口扫描 | 在更底层（iptables/nftables）做转发 |
| VPN 状态检测 | 不创建 VPN 接口，使用路由规则 |

## 8. CVD 多实例网络隔离

多开场景下，每个实例需要独立的网络出口：

```
┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│  CVD-1      │────│ 代理出口 A    │────│  IP-A        │
│  (用户 A)    │    │              │    │              │
└─────────────┘    └──────────────┘    └──────────────┘

┌─────────────┐    ┌──────────────┐    ┌──────────────┐
│  CVD-2      │────│ 代理出口 B    │────│  IP-B        │
│  (用户 B)    │    │              │    │              │
└─────────────┘    └──────────────┘    └──────────────┘
```

实现方式：

```bash
# 为每个 CVD 实例创建独立的 network namespace
# 或使用 Docker 容器封装每个 CVD + 代理的组合
docker run --privileged --network=bridge \
  -v /path/to/cvd:/cvd \
  cuttlefish:latest
```

## 总结：网络定制的核心原则

1. **一致性 > 复杂性**：网络特征必须与设备环境（定位、时区、运营商、SIM）保持一致
2. **尽量使用透明代理**：避免在 Android 系统层面留下代理配置痕迹
3. **SSL Pinning 是最大的障碍**：Frida 动态绕过用于分析，AOSP 层修改用于生产
4. **网络行为与真机差异**：注意 DNS 查询模式、连接频率、流量模式等行为特征
